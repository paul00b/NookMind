# Haptic Feedback Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add five intent-named haptic cues to the moments that matter — successful and failed mutations, star ratings, toggles, chip selection and onboarding page changes — plus a Settings switch to turn them off.

**Architecture:** A `NookHaptics` functional interface in `commonMain` maps a small semantic enum onto Compose's `HapticFeedbackType`. It is supplied through `LocalNookHaptics` from `App.kt`, reading a new `AppPreferences.hapticsEnabled` flag. When the flag is off the provided instance is a no-op, so **no call site branches on the setting**. Every cue lives in a component that exists exactly once, so the whole app inherits the feel from five small edits.

**Tech Stack:** Kotlin Multiplatform 2.4.20, Compose Multiplatform 1.8.2, multiplatform-settings 1.3.0, kotlin.test.

**Spec:** `docs/superpowers/specs/2026-09-16-haptics-design.md`

```kotlin
package fr.paulbr.nookmind.core.ui

import androidx.compose.runtime.Composable
import androidx.compose.runtime.remember
import androidx.compose.runtime.staticCompositionLocalOf
import androidx.compose.ui.hapticfeedback.HapticFeedbackType
import androidx.compose.ui.platform.LocalHapticFeedback

/**
 * Intent-named haptic cues. Call sites say what happened, never which buzz — so the whole
 * app's feel can be retuned by editing [toFeedbackType] alone.
 */
enum class HapticCue { CONFIRM, REJECT, TICK, TOGGLE_ON, TOGGLE_OFF }

fun interface NookHaptics {
    fun perform(cue: HapticCue)

    companion object {
        /** Performs nothing. Used when the user has switched vibrations off. */
        val None: NookHaptics = NookHaptics { }
    }
}

internal fun HapticCue.toFeedbackType(): HapticFeedbackType = when (this) {
    HapticCue.CONFIRM -> HapticFeedbackType.Confirm
    HapticCue.REJECT -> HapticFeedbackType.Reject
    HapticCue.TICK -> HapticFeedbackType.SegmentTick
    HapticCue.TOGGLE_ON -> HapticFeedbackType.ToggleOn
    HapticCue.TOGGLE_OFF -> HapticFeedbackType.ToggleOff
}

/**
 * Defaults to [NookHaptics.None] and must never `error()` when unprovided: ScreenshotCatalog
 * renders 35 screens through NookTheme without AppRoot, and an erroring default would break
 * `:composeApp:screenshots` for reasons that are not obvious from the stack trace.
 */
val LocalNookHaptics = staticCompositionLocalOf { NookHaptics.None }

/** Builds the instance provided by `App`. Returns the no-op when [enabled] is false. */
@Composable
fun rememberNookHaptics(enabled: Boolean): NookHaptics {
    val feedback = LocalHapticFeedback.current
    return remember(enabled, feedback) {
        if (!enabled) NookHaptics.None
        else NookHaptics { cue -> feedback.performHapticFeedback(cue.toFeedbackType()) }
    }
}
```

### Task 4: Confirm and Reject on every mutation

> **Substantially revised during review — do NOT re-execute the code below.** It shows a
> `lastCued` watermark that diffs the toast *list*. That approach shipped and was then
> replaced, because it conflated toasts raised in the same frame (taking the newest one's
> kind, so an error+success pair buzzed `Confirm` over a visible error), re-cued a live toast
> when `MainScaffold` was swapped for the Legal overlay, and — fatally — could not express

> What shipped: `ToastController` gained `cues: SharedFlow<Toast>` emitted from `show()`, plus

> `Reject` up to six times for something the user never did. Read `core/ui/Toasts.kt`.

`ToastController` is already the app's central success/error signal — 21 `success` and 12
`error` call sites, with `LibraryRepository.add`/`delete` raising theirs centrally. This
single hook therefore covers every library mutation.

```kotlin
            ToastKind.ERROR -> haptics.perform(HapticCue.REJECT)
            ToastKind.INFO -> Unit
        }
```

```kotlin
                onChange(valueFromX(offset.x))

                    if (next != hover) {
                        hover = next
                        haptics.perform(HapticCue.TICK)
                    }
                },
                onDragEnd = { hover?.let(onChange); hover = null },
                onDragCancel = { hover = null },
            )
        }
```

## Follow-up, deliberately out of scope

A second spec covers the long-press quick-action menu on library cards and pull-to-refresh
on every main screen. Both were requested and agreed. They are features rather than haptic
wiring, and both inherit this vocabulary for free — long-press activation and the
pull-to-refresh threshold are exactly the ambiguous moments haptics serve best.

Three smaller items surfaced by code review during this work, none of them caused by it:

- **`NookToggle` is inaccessible.** It is a `Box` with `.clickable` — no `Modifier.toggleable`,
  no `Role.Switch`, no `stateDescription` — so TalkBack announces every switch in the app as
  an unlabeled button with no on/off state. Affects all four toggles. A design-system fix.
- **`StarRating` swallows vertical scroll.** It uses `detectDragGestures`, which claims slop
  in every direction and consumes it before the enclosing `verticalScroll` sees it. A vertical
  swipe starting on the star row scrolls nothing. `detectHorizontalDragGestures` is the right
  primitive for a horizontal strip. Pre-existing, but haptics make an accidental interaction
  feel deliberate, which is worse.
- **Tapping the already-selected star still issues a network PATCH** and raises a success
  toast for a no-op. The haptic is now correctly silent there, but the write is not.

Also worth knowing: `gen-strings.mjs` could never run on Windows — it passed a bare absolute
path to ESM `import()`, which Node rejects. Fixed in passing during Task 9. Anyone who
regenerated strings before now did so on another machine.
